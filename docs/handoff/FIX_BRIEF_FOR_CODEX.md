### 1.1 บรรทัด ~1840-1863 — กลืน error แล้วบอกสำเร็จ (ร้ายแรงสุด)

```dart
try {
  await IncidentService.closeIncidentReport(inc.id, ...);
} catch (e) {
  debugPrint('Error closing incident: $e');   // ← กลืน แล้วไหลต่อ
}
...
setState(() => sosResolved = true);            // ← อยู่นอก try ทำงานเสมอ
_showMessage('✓ ปิดเหตุการณ์ SOS เรียบร้อยแล้ว'); // ← บอกสำเร็จเสมอ
```

RPC ล้ม → ผู้อำนวยการเห็นว่าปิดเหตุแล้ว → ไม่มีใครตามต่อ **เหตุฉุกเฉินที่ยังเปิดอยู่
ถูกเข้าใจว่าปิดแล้ว** นี่คือเหตุผลที่จัดเป็นข้อร้ายแรงที่สุดในระบบ

### 1.2 บรรทัด ~4083-4133 และ ~4764 — หยุดถูก แต่โชว์ error ดิบ

```dart
content: Text('เกิดข้อผิดพลาด: $e'),
```

`$e` ขึ้นจอ ผิดเกณฑ์ข้อ "ไม่มี error ดิบ ($e) ขึ้นจอ" ใน `AGENTS.md`
ผู้ใช้เห็นข้อความอย่าง `PostgrestException(message: ...)` ซึ่งไม่ได้บอกว่าต้องทำอะไรต่อ

### 1.3 ทั้ง 3 จุดไม่มีการอ่านกลับมาตรวจ

RPC คืน 200 แต่แถวไม่เปลี่ยน (เช่นโดน role gate ปัดตกเงียบ ๆ) ก็ยังบอกสำเร็จ

### ต้องแก้ให้เป็น

รวมทั้ง 3 จุดให้ใช้ทางเดียวกัน:

1. `catch` ต้อง **หยุด** — ห้ามไหลไปตั้ง `sosResolved = true`
2. ข้อความบนจอเป็นภาษาคน เช่น `'ปิดเหตุไม่สำเร็จ เหตุการณ์ยังเปิดอยู่'`
   ส่วน `$e` ให้ `debugPrint` เท่านั้น
3. เขียนแล้ว **อ่าน canonical กลับ** (`IncidentService.listTeacherIncidentReports()`
   หรือ `getIncidentSummary()`) แล้วตรวจว่าเหตุนั้นเป็น `resolved`/`cancelled` จริง
   ถ้าไม่เจอ → โยน `backend_close_not_confirmed` และบอกผู้ใช้ว่าสถานะยังไม่เปลี่ยน
   **ค่อยบอกสำเร็จหลังจากยืนยันแล้วเท่านั้น**

ตัวอย่างที่ทำถูกแล้วในโปรเจกต์นี้ ลอกรูปแบบได้:
`director_reports_page.dart` เมธอด `_review()` — เขียน → อ่านกลับ → ตรวจ → ค่อยบอกสำเร็จ

## 🟡 บั๊ก 2 — ไม่รู้สถานะ กลายเป็น "มาเรียน"

> **อัปเดต 2026-09-08 — บั๊ก 2:** แก้ decoder ให้ row ที่ไม่มี `status` เป็น
> `unknown` และเพิ่ม classification กลาง `isAttended` / `hasKnownStatus` แล้ว
> หน้า Parent ทั้งการมาเรียน, Dashboard และ Learning แสดง `ไม่ทราบสถานะ`
> แทนค่าดิบ และคำนวณอัตราจาก record ที่มีสถานะยืนยันแล้วเท่านั้น จึงไม่นับ unknown
> เป็นทั้งมาเรียนหรือขาดเรียน
>
> หลักฐาน: unit test ของ model **1/1 ผ่าน**; widget tests ของ Parent ที่เกี่ยวข้อง
> **17/17 ผ่าน**; full `user_app` **493 ผ่าน / 22 fail เดิม** (เพิ่ม 8 test โดยไม่เพิ่ม
> failure); full `shared_core` **47 ผ่าน / 1 fail เดิม** ใน assignment model;
> analyze ทั้งสามแพ็กเกจไม่มี error ใหม่ (`shared_core` 0, `shared_ui` 4 info,
> `user_app` 157 warning/info เดิม) เปิดเบราว์เซอร์จริงด้วยบัญชี parent แล้ว
> หน้าการมาเรียนแสดง empty state และการ์ด `ไม่ทราบสถานะ 0 คาบ` โดยไม่มี overflow
> ฐานข้อมูลปัจจุบันบังคับ attendance status เป็น NOT NULL อยู่แล้ว งานนี้จึงเป็น
> defensive hardening สำหรับ response ที่ขาด field/เปลี่ยนรูปในอนาคต ไม่มี migration
> หรือ pgTAP เพิ่ม

**ไฟล์:** `packages/shared_core/lib/models/parent_portal_model.dart` **บรรทัด 161**

```dart
status: row['status'] as String? ?? 'present',
```

backend ส่ง `status` เป็น null → ผู้ปกครองเห็นว่าลูก **"มาเรียน"** ทั้งที่ระบบไม่รู้
เป็นข้อมูลผิดแบบเงียบ ๆ ที่ไม่มีใครสังเกต

เทียบกับที่ทำถูกแล้วใน `staff_attendance_model.dart`: ไม่มีบันทึก = `no_record`
**ไม่ใช่** `present` เพราะ "ความเงียบไม่ใช่หลักฐานว่ามา"

### ต้องแก้ให้เป็น

- ทำ `status` เป็น nullable หรือใช้ค่า `'unknown'` — **ห้าม default เป็น `'present'`**
- ไล่หาทุกที่ที่ใช้ field นี้ (`grep -rn "attendance" apps/user_app/lib/pages/parent*`)
  แล้วแสดงว่า **"ไม่ทราบสถานะ"** ไม่ใช่ปล่อยให้ตกไปในช่อง "มาเรียน"
- ตัวนับสรุป (มาเรียนกี่วัน) ต้องไม่นับ unknown เป็นมาเรียน
- unit test ของ model: row ที่ไม่มี `status` ต้องไม่ออกมาเป็น present

1. **ไม่ใช่ Supabase Auth** — ทุก RPC รับ `p_token` เป็นอาร์กิวเมนต์แรก
   RPC ที่ไม่มี `p_token` เป็นของแอปอีกตัว เรียกแล้ว actor เป็น null เงียบ ๆ
2. **RLS deny-all ทุกตาราง** — `supabase.from('table').select()` คืนค่าว่างโดยไม่ error
   อ่าน/เขียนต้องผ่าน RPC เท่านั้น
3. **ลบข้อมูลปลอมแล้วต้องตามไปดูของที่เคยคู่กับมัน** — 2026-09-07 มี commit ที่ลบข้อมูล
   ปลอมออกถูกแล้ว แต่ลืมรายการตัวเลือกของตัวกรอง ทำให้เลือกแล้วรายการว่างเปล่าเงียบ ๆ
4. **`grep` พิสูจน์ได้แค่ "ไม่ต่อ backend แน่ ๆ" ไม่เคยพิสูจน์ว่า "ต่อครบแล้ว"** —
   ต้องอ่านทั้งไฟล์ก่อนสรุปว่าเสร็จ
