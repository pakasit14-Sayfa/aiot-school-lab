สิทธิ์ (role) แต่ละแบบ — มีหน้าอะไร ทำอะไรได้บ้าง apps/user_app/lib/pages/dashboard/ · เลือกหน้าโดย role_router.dart

user_app มี 8 สิทธิ์ ทุกครั้งที่ login RoleRouter จะเช็ก user.role แล้วพาไปหน้า dashboard ของสิทธิ์นั้นโดยอัตโนมัติ — คอลัมน์ "ใช้งานได้จริง" คือ feature ที่เชื่อม service/RPC แล้ว ส่วน "coming soon" คือช่องที่วาง UI ไว้แต่ยังไม่ผูก logic

หมายเหตุเรื่อง URL: แอปนี้ไม่ได้ใช้ URL router (เช่น go_router) — มี named route แค่ 5 อันในทั้งโปรเจกต์ (ทั้งหมดอยู่ใน user_app, admin_app ไม่มีเลย) หน้าที่เหลือเรียกด้วย Navigator.push(MaterialPageRoute(...)) แบบไม่ตั้งชื่อ ถ้ารันเป็น Flutter Web จะไม่เห็น URL เปลี่ยนตอนกดเข้าหน้าเหล่านั้น (URL ค้างที่ path เดิม) คอลัมน์ "URL/route" ด้านล่างจึงบอกแค่ path จริงที่มี ส่วนที่ไม่มีจะเขียนว่า "ไม่มี (push ไม่ตั้งชื่อ)"

คู่มือ Git — วิธีบันทึกและอัปงาน commit + push

1. ทำไมต้อง commit/push

บันทึกจุดที่ใช้งานได้ + สำรองงานไว้นอกเครื่อง

  • commit = จุดย้อนกลับได้ถ้าแก้พัง
  • push = สำรองงาน กันเครื่องพัง/ลบไฟล์พลาด
  • ให้เพื่อน/Codex/Claude เครื่องอื่นดึงไปทำต่อได้
  • push ขึ้น 2 ที่พร้อมกัน: GitHub (origin) และ GitLab (gitlab) กันฝั่งใดฝั่งหนึ่งมีปัญหา

2. ก่อน commit ทุกครั้ง

เช็กว่ากำลังจะบันทึกอะไรไป

  • git status — ดูไฟล์ที่แก้/ใหม่/ลบ
  • git diff — ดูเนื้อหาที่เปลี่ยนจริง ก่อน add
  • git diff --cached — ดูของที่ add แล้วรอ commit
  • ห้าม commit ไฟล์ที่มี secret เช่น env.json

3. push ขึ้น remote

อัปสิ่งที่ commit แล้วขึ้นไปเก็บจริง

  • git remote -v — เช็กก่อนว่ามี remote อะไรบ้าง
  • git push origin main — ขึ้น GitHub
  • git push gitlab main — ขึ้น GitLab
  • ถ้าถูก reject ให้ git pull ก่อน ห้าม force push ทับ
ขั้นตอนคำสั่งทำไปเพื่ออะไร
1. เลือกไฟล์ที่จะบันทึก git add packages/.../auth_service.dart เลือกทีละไฟล์/กลุ่มที่เกี่ยวข้องกัน — ห้ามใช้ git add -A หรือ git add . พร่ำเพรื่อ เพราะอาจดึงไฟล์ที่ไม่ตั้งใจ (secret, ไฟล์ทดลอง) เข้ามาด้วย
2. บันทึก (commit) git commit -m "refactor: ..." ตั้งชื่อสั้น บอกว่าทำอะไร ใช้ prefix feat: งานใหม่ · fix: แก้บั๊ก · refactor: จัดโครงสร้างใหม่ไม่เปลี่ยนพฤติกรรม · docs: แก้เอกสาร · chore: งานเบ็ดเตล็ด
3. แยก commit เป็นก้อนเล็ก add + commit ทีละเรื่อง ถ้าทำหลายเรื่องในคราวเดียว ให้แยก commit ตามเนื้อหา — เวลามีปัญหาจะ revert เฉพาะเรื่องนั้นได้ และคนอ่านประวัติ (git log) เข้าใจง่ายกว่ารวมทุกอย่างเป็นก้อนเดียว
4. push ขึ้น GitHub git push origin main อัปงานขึ้น GitHub ผ่าน SSH (ตั้ง SSH key ไว้ล่วงหน้าแล้ว)
5. push ขึ้น GitLab git push gitlab main อัปงานเดียวกันขึ้น GitLab ด้วย — เก็บสำรอง 2 ที่ และ GitLab มี CI pipeline คอย analyze/test อัตโนมัติ

ข้อควรระวัง: ห้าม commit ไฟล์ที่มี secret จริง (API key, password) · ไฟล์ที่ตั้งใจไม่ commit เช่น docs/code-structure.html นี้ ให้จำไว้ว่าอย่า git add · ไม่แน่ใจว่า commit ไหนทำอะไร ใช้ git log --oneline -10 ดูประวัติล่าสุดก่อนตัดสินใจ
